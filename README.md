# VetEnergy — Project Context

Локальное веб-приложение с аутентификацией для расчёта суточной обменной энергии кошек и собак. Проект воспроизводит исследованную логику исходного сервиса, делает формулы прозрачными, хранит питомцев и историю расчётов в PostgreSQL и не обращается к исходному API во время обычной работы.

> Расчёт является стартовой оценкой, а не ветеринарным назначением. Итоговый рацион корректируют по динамике массы, BCS, активности и клиническому состоянию животного. Особенно опасно резко ограничивать питание кошек из-за риска липидоза печени.

## Возможности

- расчёт суточной обменной энергии для взрослых животных, роста, беременности, лактации, спорта и специальных возрастных режимов;
- отдельные формулы для кошек и собак;
- справочник формул и коэффициентов в интерфейсе;
- персональные карточки питомцев и разделение данных между пользователями;
- история последних 50 расчётов;
- выбор вида, породы и пола;
- предзаполнение идеальной массы по породе и полу;
- ручная корректировка предзаполненной идеальной массы;
- автоматический пересчёт BCS из фактической и идеальной массы;
- информационная вкладка со стандартами, прямыми ссылками и словарём обозначений.

## Стек

- Next.js 16.3, App Router и Route Handlers
- React 19.2 и TypeScript
- React Hook Form 7 для связанных форм и предзаполнений
- PostgreSQL 16
- Prisma ORM 6.19
- Zod 4 для проверки API-входов
- Docker Compose для локальной базы
- ESLint и production build Next.js для проверки

### Production через Docker Compose

После локальной проверки и **ручного коммита** обновление существующего сервера:

```sh
make deploy
```

Команда отправляет текущий коммит `main` в `origin/main`, подключается по
`ssh vmerukormi` к `/var/www/vmerukormi`, обновляет только вперёд, собирает
образы, применяет миграции и перезапускает приложение. Затем проверяет здоровье
контейнера и перечитывает Nginx. При ошибке миграции приложение не перезапускает.
Нужны настроенный SSH-ключ, доступ к Git, Docker Compose и `flock` на сервере.
Незакоммиченные файлы, другая ветка и расхождение истории останавливают деплой.
Автокоммита, seed, сброса базы, удаления томов и резервного копирования нет.
Ошибку после применения миграций исправляют новым коммитом, автоматического
отката схемы нет. При нехватке диска сборка остановится; тома не очищаются.
Адрес и каталог можно переопределить: `make deploy DEPLOY_HOST=vmerukormi DEPLOY_DIR=/var/www/vmerukormi`.

Единицы нутриентов и правила миграции: `backend/database/prisma/catalog/reference/README.md`.

На VPS проект размещается в `/var/www/vmerukormi`. Файл `compose.prod.yml` поднимает PostgreSQL, применяет миграции, запускает standalone-сборку Next.js и публикует её через Nginx. PostgreSQL не имеет публичного порта.

```bash
cd /var/www/vmerukormi
cp .env.production.example .env.production
# Заменить все тестовые значения в .env.production.
docker compose --env-file .env.production -f compose.prod.yml up -d --build
docker compose --env-file .env.production -f compose.prod.yml ps
```

Обновление приложения:

```bash
cd /var/www/vmerukormi
git pull --ff-only
docker compose --env-file .env.production -f compose.prod.yml up -d --build
```

Контейнер `migrate` выполняет `prisma migrate deploy` до запуска приложения. `make seed` в production запускать нельзя: команда создаёт демонстрационные данные и локального администратора с небезопасным паролем.

При первичной настройке `NGINX_MODE=http` используется HTTP-конфигурация.
После выпуска сертификата переключить `NGINX_MODE=https` и
`AUTH_COOKIE_SECURE=true`, как описано в [инструкции HTTPS](docs/https.md).
Указывать `--env-file .env.production` обязательно: он выбирает конфигурацию
Nginx, а не только переменные внутри приложения. На текущем VPS HTTPS уже включён.

Остановка:

```bash
docker compose -f backend/docker-compose.yml stop
```

Удаление Docker volume уничтожит локальные данные PostgreSQL. Не используйте `docker compose -f backend/docker-compose.yml down -v`, если данные нужны.

## Вход в приложение

После применения миграций доступна начальная локальная учётная запись:

```text
Email: admin@vetenergy.ru
Пароль: 123456
```

Этот пароль намеренно создан по запросу для локальной разработки и слишком слаб для публичной среды. Перед развёртыванием его необходимо заменить.

Для локальной проверки двух независимых кабинетов выполните `npm run db:seed-users`:
`user1@vetenergy.test` и `user2@vetenergy.test`, пароль у обоих `123456`.
Команда не меняет существующие пароли и не восстанавливает удалённые аккаунты.

Регистрация доступна на `/register`: уникальный email, пароль и автономная ALTCHA.
Письма и подтверждение почты пока отключены. Администратор управляет аккаунтами
на `/users`, смотрит журнал на `/audit`; восстановление бизнес-записей — `/archive`.
Справочник нутриентов изменяет только администратор; пользователь выбирает
существующие нутриенты и задаёт их количество в своих продуктах.
Роли, миграции, снимки рационов и проверки описаны в `docs/authentication.md`.

Пароли хранятся в виде `scrypt`-хешей. Сессия хранится в PostgreSQL, а браузер получает случайный непрозрачный токен в `HttpOnly` cookie. Все изменяющие API-запросы дополнительно требуют CSRF-токен и проходят проверку `Origin`. Пользовательские записи фильтруются по владельцу на сервере; проверки интерфейса не являются единственной линией защиты.

## Архитектура

```text
Браузер
  └─ FSD frontend: app → _pages → features → entities → shared
       └─ /api/* — обязательные тонкие Route Handlers Next.js
            └─ backend/http
                 ├─ Zod validation
                 ├─ backend/domain
                 └─ backend/infrastructure → Prisma → PostgreSQL
```

Frontend организован по Feature-Sliced Design. Экранные композиции находятся в `src/_pages`, чтобы не включать Next.js Pages Router. Правила импортов и локальные решения описаны в [docs/architecture.md](docs/architecture.md). Официальный проектный skill находится в `.agents/skills/feature-sliced-design/SKILL.md`.

Основные каталоги:

```text
src/
  app/                       Next.js composition, routing and API adapters
  _pages/                    экранные композиции и локальная логика
  features/                  пользовательские действия
  entities/                  Pet, Breed, Calculation, Module, Reference
  shared/                    HTTP-клиент и переиспользуемый UI
backend/
  http/                      серверные HTTP-handlers и Zod-схемы
  domain/nutrition/          формулы и расчётные модули
  infrastructure/database/  Prisma Client singleton
  database/prisma/           schema, migrations, seed и breeds.json
  docker-compose.yml         локальный PostgreSQL 16
```

Файлы `src/app/api/**/route.ts` нельзя физически перенести из `app`: Next.js распознаёт Route Handlers только там. Они не содержат реализации и только реэкспортируют обработчики из `backend/http`.

## Предзаполнение породы, пола, веса и BCS

Исследованное поведение исходного приложения устроено так:

```text
порода + пол → ориентир идеальной массы
фактическая масса + идеальная масса → BCS
идеальная масса + физиологический модуль → калорийность
```

Это не зависимость `BCS → идеальная масса`.

На фронтенде обе формы построены на React Hook Form. При выборе породы и пола соответствующий норматив записывается в `idealWeight`. Пользователь может изменить его вручную для конкретного животного. После изменения `actualWeight` или `idealWeight` BCS пересчитывается автоматически:

```text
BCS = clamp(round(5 + (AW / IW - 1) × 10), 1, 9)
```

Примеры:

| AW / IW | BCS |
|---:|---:|
| 0.60 | 1 |
| 0.80 | 3 |
| 1.00 | 5 |
| 1.20 | 7 |
| 1.40 и выше | 9 |

Проверенный пример для британской короткошёрстной:

- самец: предзаполненный `IW = 5 кг`;
- самка: предзаполненный `IW = 4 кг`;
- самец с `AW = 7 кг` и `IW = 5 кг`: `BCS = 9`.

BCS хранится вместе с расчётом и используется для оценки состояния, но в текущих формулах калорийности напрямую не умножает результат. Для взрослых модулей ключевым входом является идеальная масса.

## Работа с рационом

Рацион создаётся в разделе `/rations` и может быть сразу связан с питомцем. Если у питомца есть сохранённый расчёт энергии, его последнее значение предлагается как суточная цель.

В конструкторе `/rations/:id` продукты добавляются в граммах или пользовательских мерах. Для каждой включённой позиции приложение мгновенно рассчитывает вклад в энергию, белок, жиры, углеводы и заполненные нутриенты:

```text
вклад продукта = значение на базовое количество × граммы / базовое количество
```

В суточном режиме итоги сравниваются с целью напрямую. В недельном режиме позиции распределяются по дням недели, а энергетическая и нутриентная сводка показывает среднее значение в сутки. Выключенная позиция остаётся в составе, но не участвует в итогах.

Целевые диапазоны для отдельных витаминов, минералов и аминокислот пока не заданы, поэтому для них показывается сумма без статуса дефицита или избытка.

## Формулы калорийности

Обозначения:

- `AW` — фактическая масса, кг;
- `IW` — идеальная или ожидаемая взрослая масса, кг;
- `ОЭ / ME` — обменная энергия;
- `BCS` — Body Condition Score, шкала 1–9;
- `exp(x)` — экспонента `e^x`;
- `L` — коэффициент недели лактации;
- `n`, `m` — группы детёнышей;
- `energyFactor` — пользовательская поправка ОЭ.

Итоговый алгоритм:

```text
baseEnergy = формула выбранного модуля
adjustedEnergy = round(baseEnergy × energyFactor)
```

Оба результата округляются до целых ккал/сут.

| Модуль | Формула базовой энергии |
|---|---|
| Кошка, взрослая | `100 × IW^0.67` |
| Кошка, сеньор кардио | `100 × IW^0.67` |
| Кошка, беременность | `140 × IW^0.67` |
| Кошка, котёнок | `100 × AW^0.67 × 6.7 × (exp(-0.189 × AW/IW) - 0.66)` |
| Кошка, лактация | `100 × IW^0.67 + IW × Kдет × L` |
| Собака, взрослая | `100 × IW^0.75` |
| Собака, сеньор кардио | `90 × IW^0.75` |
| Собака, спорт и работа | `100 × IW^0.75` |
| Собака, беременность I | `132 × IW^0.75` |
| Собака, беременность II | `130 × IW^0.75 + 26 × IW` |
| Щенок, фаза 1 | `100 × AW^0.75 × 3.2 × (exp(-0.87 × AW/IW) - 0.1)` |
| Щенок, фаза 2 | та же формула ОЭ, нутриентные нормы могут различаться |
| Собака, лактация | `100 × IW^0.75 + IW × (24n + 12m) × L` |

Кошачья лактация:

- `Kдет = 18`, если детёнышей меньше 3;
- `Kдет = 60`, если 3–4;
- `Kдет = 70`, если 5 и больше;
- `L = 0.9` для недель 1–2;
- `L = 1.2` для недель 3–4;
- `L = 1.1` для недели 5;
- далее `L = 1`.

Собачья лактация:

- `n = min(число щенков, 4)`;
- `m = min(max(число щенков - 4, 0), 4)`;
- `L = 0.75`, `0.95`, `1.1`, `1.2` для недель 1, 2, 3 и 4+ соответственно.

## Схема базы данных

### `Module`

Справочник 13 расчётных модулей: идентификатор, название, вид, формула и описание.

### `Breed`

Справочник пород: вид, русское и английское название, ориентир идеальной массы самца и самки. Идентификаторы соответствуют исследованному справочнику.

### `Pet`

Карточка питомца: имя, вид, пол, порода, фактическая масса, идеальная масса, BCS, дата рождения, заметка и временные метки. Удаление породы устанавливает `breedId = null`.

### `Calculation`

Неизменяемый снимок входов и результата: питомец, модуль, массы, BCS, поправка ОЭ, лактация, число детёнышей, базовая и скорректированная энергия. При удалении питомца история сохраняется, а `petId` становится `null`.

Связи:

```text
Breed 1 ─── N Pet
Pet   1 ─── N Calculation
Module 1 ── N Calculation
```

## Миграции и seed

В проекте две последовательные миграции, покрывающие четыре таблицы:

1. `20260805204122_init` — enum `Species`, таблицы `Module`, `Pet`, `Calculation`, индексы и внешние ключи.
2. `20260805222240_add_breeds_and_sex` — enum `Sex`, таблица `Breed`, поля `Pet.breedId` и `Pet.sex`, индекс и внешний ключ.

`backend/database/prisma/seed.ts` выполняет idempotent upsert:

- 13 модулей из `backend/domain/nutrition/modules.ts`;
- 243 породы из `backend/database/prisma/breeds.json`.

Повторный `npm run db:seed` не создаёт дубликаты.

## API

### Породы

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/breeds` | Все породы по русскому названию |
| `GET` | `/api/breeds?species=CAT` | Только кошки |
| `GET` | `/api/breeds?species=DOG` | Только собаки |

### Модули

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/modules` | 13 доступных модулей и формул |

### Питомцы

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/pets` | Список питомцев с породой |
| `POST` | `/api/pets` | Создание карточки |
| `PATCH` | `/api/pets/:id` | Частичное изменение |
| `DELETE` | `/api/pets/:id` | Удаление карточки |

Пример создания:

```json
{
  "name": "Барсик",
  "species": "CAT",
  "sex": "MALE",
  "breedId": "3de51955-b976-4433-bc38-758a27c6a6cf",
  "actualWeight": 7,
  "idealWeight": 5,
  "bcs": 9
}
```

### Расчёты

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/calculations` | Последние 50 расчётов |
| `POST` | `/api/calculations` | Рассчитать и опционально сохранить |
| `DELETE` | `/api/calculations/:id` | Удалить расчёт |

Пример без сохранения:

```json
{
  "petId": null,
  "moduleId": "cat-adult",
  "actualWeight": 7,
  "idealWeight": 5,
  "bcs": 9,
  "energyFactor": 1,
  "lactationWeek": 1,
  "childrenCount": 0,
  "save": false
}
```

Ответ:

```json
{
  "baseEnergy": 294,
  "adjustedEnergy": 294
}
```

## Источники и стандарты

### Общий каталог базовых продуктов

Миграции добавляют 24 отобранных продукта health-diet и 1555 значений состава. Каталог доступен всем пользователям без копирования при регистрации; общие записи редактирует только ADMIN, личные продукты остаются личными. Поиск в «Продуктах» учитывает названия тегов, есть отдельный фильтр по тегу. Состав, влага и обязательные нутриенты выводятся в рационе и Excel, отсутствующие данные отмечаются явно.

Установка: `npm run db:deploy` (в production выполняется сервисом `migrate`). Сеть и повторный парсинг при запуске не требуются. Подробности отбора, единиц и воспроизводимости: [health-diet](backend/database/prisma/catalog/health-diet/README.md).

Проверки: `npm run test:catalog`. Интеграционный сценарий `tooling/catalog-smoke.mjs` запускается только с изолированной базой `catalog_test` и локальным тестовым сервером через переменные `DATABASE_URL` и `CATALOG_TEST_APP_URL`; создаёт и удаляет собственных тестовых пользователей.

- [FEDIAF Nutritional Guidelines 2025](https://www.europeanpetfood.org/wp-content/uploads/2025/09/FEDIAF-Nutritional-Guidelines_2025.pdf), раздел 7.2 Energy.
- [NRC: Nutrient Requirements of Dogs and Cats](https://www.nationalacademies.org/publications/10668).
- [AAHA: Energy Requirement Calculations](https://www.aaha.org/globalassets/02-guidelines/2021-nutrition-and-weight-management/resourcepdfs/nutritiongl_box1.pdf).
- [Merck Veterinary Manual: Daily Maintenance Energy Requirements](https://www.merckvetmanual.com/multimedia/table/daily-maintenance-energy-requirements-for-dogs-and-cats).

Структура уравнений сопоставлена с открытыми стандартами. Конкретные модули, коэффициенты, предзаполненные веса и дискретный расчёт BCS дополнительно сверялись с ответами исходного API на синтетических данных.

## Ограничения и принятые решения

- Нет самостоятельной регистрации, восстановления пароля и управления пользователями через UI.
- Есть роли `ADMIN` и `USER`, но пока нет отдельной матрицы разрешений, журнала изменений и резервного копирования.
- UI собран в одном крупном `dashboard.tsx`; при расширении его стоит разделить по вкладкам и формам.
- Идеальная масса породы — ориентир, а не индивидуальный диагноз.
- BCS вычисляется только по отношению масс; клиническая оценка также требует визуального осмотра и пальпации.
- BCS не изменяет калорийность напрямую; взрослые формулы используют `IW`.
- `cat-senior-cardio` сейчас использует ту же энергетическую формулу, что и взрослая кошка.
- Две фазы роста щенка имеют одинаковую формулу ОЭ; различия могут быть в нутриентных нормах, которые приложение пока не рассчитывает.
- История ограничена последними 50 записями.
- Есть тесты FSD, парсера, прав каталога, агрегации нутриентов и интеграционный сценарий каталога; остальные сценарии пока проверяются вручную.
- Локальные credentials PostgreSQL нельзя использовать в production.
