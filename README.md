# VetEnergy — Project Context

Локальное веб-приложение с аутентификацией для расчёта суточной обменной энергии кошек и собак. Проект воспроизводит исследованную логику исходного сервиса, делает формулы прозрачными, хранит питомцев и историю расчётов в PostgreSQL и не обращается к исходному API во время обычной работы.

> Расчёт является стартовой оценкой, а не ветеринарным назначением. Итоговый рацион корректируют по динамике массы, BCS, активности и клиническому состоянию животного. Особенно опасно резко ограничивать питание кошек из-за риска липидоза печени.

## Возможности

- расчёт суточной обменной энергии для взрослых животных, роста, беременности, лактации, спорта и специальных возрастных режимов;
- отдельные формулы для кошек и собак;
- справочник формул и коэффициентов в интерфейсе;
- персональные карточки питомцев и разделение данных между пользователями;

- выбор вида, породы и пола;

- ручная корректировка предзаполненной идеальной массы;
- автоматический пересчёт BCS из фактической и идеальной массы;
- информационная вкладка со стандартами, прямыми ссылками и словарём обозначений.

### Production через Docker Compose

На VPS проект размещается в `/var/www/vmerukormi`. Файл `compose.prod.yml` поднимает PostgreSQL, применяет миграции, запускает standalone-сборку Next.js и публикует её через Nginx. PostgreSQL не имеет публичного порта.

```bash
cd /var/www/vmerukormi
cp .env.production.example .env.production
# Заменить все тестовые значения в .env.production.
docker compose -f compose.prod.yml up -d --build
docker compose -f compose.prod.yml ps
```

Обновление приложения:

```bash
cd /var/www/vmerukormi
git pull --ff-only
docker compose -f compose.prod.yml up -d --build
```

Контейнер `migrate` выполняет `prisma migrate deploy` до запуска приложения. `make seed` в production запускать нельзя: команда создаёт демонстрационные данные и локального администратора с небезопасным паролем.

Текущая конфигурация Nginx принимает HTTP на порту 80 и предназначена для первичной проверки. Для работы защищённых cookie и авторизации в production необходимо привязать домен и включить HTTPS до публичного запуска.

До подключения HTTPS можно временно использовать `AUTH_COOKIE_SECURE=false` в `.env.production`. После включения HTTPS значение необходимо заменить на `true` и пересоздать контейнер приложения.

Остановка:

```bash
docker compose -f backend/docker-compose.yml stop
```

Удаление Docker volume уничтожит локальные данные PostgreSQL. Не используйте `docker compose -f backend/docker-compose.yml down -v`, если данные нужны.

## Вход в приложение

После применения миграций доступна начальная локальная учётная запись:

```text
Пользователь: admin
Пароль: 123456
```

Этот пароль намеренно создан по запросу для локальной разработки и слишком слаб для публичной среды. Перед развёртыванием его необходимо заменить.

Пароли хранятся в виде `scrypt`-хешей. Сессия хранится в PostgreSQL, а браузер получает случайный непрозрачный токен в `HttpOnly` cookie. Все изменяющие API-запросы дополнительно требуют CSRF-токен и проходят проверку `Origin`. Пользовательские записи фильтруются по владельцу на сервере; проверки интерфейса не являются единственной линией защиты.

Правила импортов и локальные решения описаны в [docs/architecture.md](docs/architecture.md). Официальный проектный skill находится в `.agents/skills/feature-sliced-design/SKILL.md`.

## Предзаполнение породы, пола, веса и BCS

Исследованное поведение исходного приложения устроено так:

```text
порода + пол → ориентир идеальной массы
фактическая масса + идеальная масса → BCS
идеальная масса + физиологический модуль → калорийность
```

Это не зависимость `BCS → идеальная масса`.

На фронтенде обе формы построены на React Hook Form. При выборе породы и пола соответствующий норматив записывается в `idealWeight`. Пользователь может изменить его вручную для конкретного животного. После изменения `actualWeight` или `idealWeight` BCS пересчитывается автоматически:

```text
BCS = clamp(round(5 + (AW / IW - 1) × 10), 1, 9)
```

Примеры:

| AW / IW | BCS |
|---:|---:|
| 0.60 | 1 |
| 0.80 | 3 |
| 1.00 | 5 |
| 1.20 | 7 |
| 1.40 и выше | 9 |

Проверенный пример для британской короткошёрстной:

- самец: предзаполненный `IW = 5 кг`;
- самка: предзаполненный `IW = 4 кг`;
- самец с `AW = 7 кг` и `IW = 5 кг`: `BCS = 9`.

BCS хранится вместе с расчётом и используется для оценки состояния, но в текущих формулах калорийности напрямую не умножает результат. Для взрослых модулей ключевым входом является идеальная масса.

## Работа с рационом

Рацион создаётся в разделе `/rations` и может быть сразу связан с питомцем. Если у питомца есть сохранённый расчёт энергии, его последнее значение предлагается как суточная цель.

В конструкторе `/rations/:id` продукты добавляются в граммах или пользовательских мерах. Для каждой включённой позиции приложение мгновенно рассчитывает вклад в энергию, белок, жиры, углеводы и заполненные нутриенты:

```text
вклад продукта = значение на базовое количество × граммы / базовое количество
```

В суточном режиме итоги сравниваются с целью напрямую. В недельном режиме позиции распределяются по дням недели, а энергетическая и нутриентная сводка показывает среднее значение в сутки. Выключенная позиция остаётся в составе, но не участвует в итогах.

Целевые диапазоны для отдельных витаминов, минералов и аминокислот пока не заданы, поэтому для них показывается сумма без статуса дефицита или избытка.

## Формулы калорийности

Обозначения:

- `AW` — фактическая масса, кг;
- `IW` — идеальная или ожидаемая взрослая масса, кг;
- `ОЭ / ME` — обменная энергия;
- `BCS` — Body Condition Score, шкала 1–9;
- `exp(x)` — экспонента `e^x`;
- `L` — коэффициент недели лактации;
- `n`, `m` — группы детёнышей;
- `energyFactor` — пользовательская поправка ОЭ.

Итоговый алгоритм:

```text
baseEnergy = формула выбранного модуля
adjustedEnergy = round(baseEnergy × energyFactor)
```

Оба результата округляются до целых ккал/сут.

| Модуль | Формула базовой энергии |
|---|---|
| Кошка, взрослая | `100 × IW^0.67` |
| Кошка, сеньор кардио | `100 × IW^0.67` |
| Кошка, беременность | `140 × IW^0.67` |
| Кошка, котёнок | `100 × AW^0.67 × 6.7 × (exp(-0.189 × AW/IW) - 0.66)` |
| Кошка, лактация | `100 × IW^0.67 + IW × Kдет × L` |
| Собака, взрослая | `100 × IW^0.75` |
| Собака, сеньор кардио | `90 × IW^0.75` |
| Собака, спорт и работа | `100 × IW^0.75` |
| Собака, беременность I | `132 × IW^0.75` |
| Собака, беременность II | `130 × IW^0.75 + 26 × IW` |
| Щенок, фаза 1 | `100 × AW^0.75 × 3.2 × (exp(-0.87 × AW/IW) - 0.1)` |
| Щенок, фаза 2 | та же формула ОЭ, нутриентные нормы могут различаться |
| Собака, лактация | `100 × IW^0.75 + IW × (24n + 12m) × L` |

Кошачья лактация:

- `Kдет = 18`, если детёнышей меньше 3;
- `Kдет = 60`, если 3–4;
- `Kдет = 70`, если 5 и больше;
- `L = 0.9` для недель 1–2;
- `L = 1.2` для недель 3–4;
- `L = 1.1` для недели 5;
- далее `L = 1`.

Собачья лактация:

- `n = min(число щенков, 4)`;
- `m = min(max(число щенков - 4, 0), 4)`;
- `L = 0.75`, `0.95`, `1.1`, `1.2` для недель 1, 2, 3 и 4+ соответственно.

## Схема базы данных

### `Module`

Справочник 13 расчётных модулей: идентификатор, название, вид, формула и описание.

### `Breed`

Справочник пород: вид, русское и английское название, ориентир идеальной массы самца и самки. Идентификаторы соответствуют исследованному справочнику.

### `Pet`

Карточка питомца: имя, вид, пол, порода, фактическая масса, идеальная масса, BCS, дата рождения, заметка и временные метки. Удаление породы устанавливает `breedId = null`.

### `Calculation`

Неизменяемый снимок входов и результата: питомец, модуль, массы, BCS, поправка ОЭ, лактация, число детёнышей, базовая и скорректированная энергия. При удалении питомца история сохраняется, а `petId` становится `null`.

Связи:

```text
Breed 1 ─── N Pet
Pet   1 ─── N Calculation
Module 1 ── N Calculation
```

## Ограничения и принятые решения

- Нет самостоятельной регистрации, восстановления пароля и управления пользователями через UI.
- Есть роли `ADMIN` и `USER`, но пока нет отдельной матрицы разрешений, журнала изменений и резервного копирования.
- UI собран в одном крупном `dashboard.tsx`; при расширении его стоит разделить по вкладкам и формам.
- Идеальная масса породы — ориентир, а не индивидуальный диагноз.
- BCS вычисляется только по отношению масс; клиническая оценка также требует визуального осмотра и пальпации.
- BCS не изменяет калорийность напрямую; взрослые формулы используют `IW`.
- `cat-senior-cardio` сейчас использует ту же энергетическую формулу, что и взрослая кошка.
- Две фазы роста щенка имеют одинаковую формулу ОЭ; различия могут быть в нутриентных нормах, которые приложение пока не рассчитывает.
- История ограничена последними 50 записями.
- Есть тесты FSD, парсера, прав каталога, агрегации нутриентов и интеграционный сценарий каталога; остальные сценарии пока проверяются вручную.
- Локальные credentials PostgreSQL нельзя использовать в production.

## Следующие разумные шаги

1. Разделить `dashboard.tsx` на компоненты и вынести form hooks.
2. Добавить unit-тесты для всех 13 формул и граничных значений BCS.
3. Добавить интеграционные тесты Route Handlers с тестовой PostgreSQL.
4. Валидировать соответствие `breedId` выбранному виду на backend.
5. Добавить режим безопасного снижения веса как отдельную модель, а не скрытую поправку.
6. Показывать источник и версию формулы рядом с результатом.
7. Добавить экспорт истории в CSV/XLSX.
8. Настроить production-переменные, резервные копии и отдельного ограниченного пользователя БД перед развёртыванием.
9. Добавить смену и восстановление пароля, ограничение частоты попыток входа и управление активными сессиями.

Токен исходного исследованного сайта ранее был опубликован в переписке. Его необходимо отозвать и выпустить новый. Приложение не хранит и не использует этот токен во время работы.
