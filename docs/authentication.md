# Учётные записи, права и сохранность данных

## Принятые решения

- Вход по нормализованному email и паролю. Пробелы по краям и регистр email
  не создают новый адрес. Уникальность действует и для удалённых аккаунтов.
- Регистрация сразу активирует роль `USER`. Проверка email, приглашения,
  уведомления и самостоятельный сброс пароля по почте пока отсутствуют.
- Администратор создаёт аккаунт с постоянным паролем и передаёт его лично.
  Может менять имя, email, пароль, роль, удалять и восстанавливать пользователя.
- `ADMIN` видит и изменяет любые доступные бизнес-записи, `USER` — собственные.
  Общий каталог доступен для чтения всем; редактирование общего каталога — админу.
  Справочник нутриентов создаёт, редактирует, удаляет и восстанавливает только админ.
  Пользователь управляет количеством существующих нутриентов в собственном продукте.
- Последнего активного администратора нельзя удалить или понизить. Проверка
  сериализована транзакционной блокировкой PostgreSQL, включая повторную проверку
  полномочий после получения блокировки.
- Удаление аккаунта и смена email, пароля или роли отзывают сессии. Восстановление
  требует нового входа и сохраняет прежний пароль, если админ не задал другой.

## Начальные учётные записи

Миграции на чистой БД создают `admin@vetenergy.ru` с паролем `123456`.
Миграция обновления сохраняет прежний хеш пароля существующего bootstrap-admin.
Адрес не обязан реально существовать, поскольку доставки писем нет.
Принудительной смены пароля нет; известный слабый пароль небезопасен для
публичного сайта и может вызывать предупреждение менеджера паролей браузера.

`npm run db:seed-users` создаёт только локальные `user1@vetenergy.test` и
`user2@vetenergy.test` с паролем `123456`. Повторный запуск ничего не сбрасывает.
Тестовые аккаунты не создаются production-миграцией или деплоем.
Старые аккаунты без email получают уникальный `legacy-<hex-id>@vetenergy.test`,
их пароли сохраняются. Имя переносится из прежнего username.

## Капча и ограничения частоты

ALTCHA работает с локальным серверным challenge и проверкой proof-of-work,
без внешних сервисов, API-ключей, аналитики или запросов к провайдеру.
Случайный секрет и параметры каждого challenge хранятся в PostgreSQL.
Решение принимается однократно, срок действия — 20 минут; параметры проверки
берутся из БД, а не из присланного клиентом payload.
Ошибочная регистрация также расходует успешно проверенный challenge.

За 15 минут разрешены 100 попыток входа на адрес, 15 на email, 20 регистраций
и 60 запросов капчи на адрес. Счётчики общие для экземпляров приложения,
в БД хранится хеш ключа ограничения, а не сырой IP. Просроченные технические
записи удаляются при выдаче следующего challenge, сессии — при создании сессии.
Это ограничение злоупотреблений, не полноценная защита от распределённого DDoS.

В production контейнер принимает запросы только через Nginx, который заменяет
`X-Real-IP`; `TRUST_PROXY=true` включён в `compose.prod.yml`. Не включать этот
флаг при прямом публичном доступе к Next.js. Без него применяется общий локальный
лимит, а клиентский заголовок не считается доверенным.

ALTCHA требует Web Crypto: HTTPS либо localhost/127.0.0.1. До публичного запуска
нужно настроить HTTPS и `AUTH_COOKIE_SECURE=true`. На обычном HTTP-адресе VPS
регистрация с капчей не поддерживается. Локальная разработка не требует ключей.
На HOSTKEY с 19.11.2026 включён HTTPS для `vetenergy.ru`, `www.vetenergy.ru`
и `195.10.205.158`, используются защищённые cookie. При переходе с IP на домен
нужно войти заново: cookie привязаны к имени хоста. Настройка и автопродление
описаны в [инструкции HTTPS](https.md).

## Мягкое удаление

Бизнес-таблицы имеют `deletedAt`, `deletedById`. В обычном прикладном клиенте БД
`delete`/`deleteMany` превращаются в обновление этих полей; активные выборки,
вложенные списки и счётчики исключают удалённые строки.
Для явного доступа к истории используется `deletedAt: {}`, к архиву —
`deletedAt: { not: null }`. Ссылки «многие к одному» не скрываются автоматически:
историческая запись не должна терять свой продукт, питомца или расчёт.
При выборе новой связи обработчик обязан проверять активность родителя.

Связанные бизнес-записи защищены внешними ключами `ON DELETE RESTRICT`.
Удаление пользователя не удаляет его продукты, питомцев или рационы.
Архив восстанавливает только выбранную запись; для дочерней записи сначала
нужно восстановить родителя. Пользователь восстанавливает своё, админ — любое;
учётные записи восстанавливаются отдельно на странице пользователей.

Сессии, задания капчи и счётчики ограничений удаляются физически.
`rawPrisma` разрешён инфраструктуре, миграциям и техническим операциям; он
обходит прикладную фильтрацию, поэтому не использовать его для обычного CRUD.
Вложенные `delete`/`deleteMany` запрещены. Транзакции только callback-формы:
массив уже запущенных операций не обеспечивает атомарность этого адаптера.

## Исторический состав рациона

`RationItem.productSnapshot` хранит версию схемы, название продукта, базовую массу,
калорийность, БЖУ, нутриенты с названиями и единицами и меры веса. Снимок создаётся
при добавлении продукта или явной замене продукта в позиции.
Изменение количества использует сохранённую меру, а не её текущее значение.
Переименование, изменение состава или удаление исходного продукта не меняет
сохранённый рацион, итоговые значения и Excel. Удалённый продукт открывается
с пометкой и без редактирования, но исключается из меню нового добавления.

Миграция заполняет снимки уже существующих строк по составу на момент обновления.
Историю изменений, которой раньше не было в БД, восстановить невозможно.
Для старой меры сохраняется историческое отношение grams/quantity.

## Журнал действий

`AuditEvent` хранит автора, время, действие, тип и идентификатор записи,
идентификатор запроса, данные до изменения и результат с изменёнными полями.
Создание, правка, удаление и восстановление пишутся в той же транзакции:
откат бизнес-операции откатывает запись журнала. Для массовой операции «до» —
массив строк, «после» — число изменённых строк и применённые поля.
Вложенные создания включены в изменения родительской записи.

Дополнительно фиксируются регистрация, вход, неудачный вход, выход и экспорт.
Неудачный вход записывается отдельно от откатываемой транзакции запроса.
Пароли, их хеши, cookie, токены и секреты капчи отбрасываются рекурсивно.
Журнал доступен только администратору. Он может содержать контактные данные
клиентов в снимках; не публиковать его. Просмотры страниц не отслеживаются.
Автоматического удаления или отдельного неизменяемого внешнего хранилища
аудита пока нет: администратор самой БД технически может изменить журнал.

## Миграции и проверки

Применённые миграции не редактировать. `prisma migrate deploy` читает
`_prisma_migrations` и применяет только новые, а не повторно все файлы.
Не использовать reset, db push или полный демонстрационный seed на сервере.

```sh
npm run db:deploy
npm run db:generate
npm run db:seed-users
npm run dev
npm run test:accounts
npm run test:accounts:integration
npm run lint
npm run build
```

Интеграционные проверки разрешены только на localhost. Созданные ими QA-записи
удаляются мягко и остаются в локальном архиве. `test:accounts:migration` принимает
`TEST_DATABASE_URL` строго пустой локальной БД с суффиксом `_test` и никогда
не очищает существующую базу; проверяет старые аккаунты, снимки, внешние ключи
и повторный запуск сидера без сброса пароля.
